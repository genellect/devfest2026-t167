# バックエンドの契約と検証

## 認証と権限

生徒・教師とも Firebase の `google.com` ID token が必須。API は無効化・失効も確認する。部屋作成は `teacher: true` の管理者設定の custom claim を要求し、教師操作には部屋の moderator 所属も必要。画面の役割選択では権限を付与しない。教師権限は信頼された管理者だけが Admin SDK で設定する。ローカルでは `firebase/seed.mjs` が模擬Googleユーザーに付与する。一般ユーザーに claim 設定用のAPIは公開しない。

Google Docs のインフラ手順書とその写しには「参加者は匿名」の旧方針が残る。生徒もGoogle必須という依頼者の明示指示を、この実装では優先した。Google Docs の正本・本番設定は変更していない。公開前には正本・認証プロバイダー設定との同期が必要。

## 進行と保存

- 部屋は collecting → discussing → consensus → closed。一段ずつ教師が進める。
- グループは opinions → discussing → consensus → done。全員提出で開始、欠席時は教師が開始できる。
- closed の書き込みと分析結果の保存は拒否する。進行中の古いジョブは jobId が一致する場合だけ保存する。
- 意見の更新・移動は議論開始前だけ。結論の一文は分析中と結果確定後には更新できない。部屋全体の合意分析が実行中・完了後の変更も拒否する。停止したジョブは教師が60秒後に再実行して回復させる。確定後は409を返し、分析結果と入力の食い違いを防ぐ。
- グループ結果の出し直しは教師が実施する。回答がそろわないときの教師による確定では、未提出者のあとからの提出も受け付けない。
- 新規の部屋は schemaVersion=2。複数グループのメンバーは role+group の索引で絞り、その利用者の回答だけを読む。同一プロセスでは部屋ごとの短いDB集計更新を直列にし、競合による再試行を減らす（待機64件まで）。これは性能上の補助で、複数プロセスでの正しさはDBトランザクションとjobIdで守る。旧形式の部屋は group 省略=1 の互換処理を使う。データの一括書き換えは不要。
- Rules と API はGoogle認証・所属・本人の回答・グループ・終了状態をそれぞれ検査する。Admin SDK を使うAPIはRulesを通らないため、API側の認可を省略しない。

## 制限と障害

| 操作 | 制限・再送 |
|---|---|
| 部屋作成 | 利用者ごと1時間に10回 |
| 参加コード照合 | 利用者ごと1分に30回 |
| 部屋へのAPI操作 | 利用者ごと1分に120回 |
| 論点・合意分析 | 対象の分析ごと30秒間隔、同時実行のリースは60秒 |
| 録音分析 | 12MiB、30分+1分の猶予、グループごと最大3試行、失敗後30秒待機 |
| 音声ファイル解析 | 送信/分析中の音声は本文受信前に4件までに制限。解析は同時2件/プロセス、Worker 48MiBのV8ヒープ上限、5秒。APIのイベントループから分離 |

利用者単位の操作制限は Firestore の `apiLimits` で共有し、プロセスが増えても適用する。保存文書は利用者と操作の組ごとに1件で、時間窓ごとには増やさない。待機可能な429応答には Retry-After を付ける。異常なJSON・過大本文は400/413、認証不成立401、権限不足403、状態競合409、AI障害503。本文やSDKの例外をエラー・ログへ出さない。

Gemini のテキスト処理は総予算20秒以内で429/502/503/504だけ1回再試行する。音声分析は費用の重複を抑えるため自動再試行せず180秒で打ち切る。SDKの暗黙の5回再試行を無効化し、タイマーを必ず解除する。AbortSignalでクライアント側の通信を中断しても、Google側の処理・課金停止を保証するものではない（SDKの契約）。モデル・思考レベルは変更しない。

AIの合意分類は、入力番号が範囲内で、重複・欠落のない完全な分割であること、提案IDが既知で重複しないことを検証する。入力に含まれる命令は引用データとして扱うよう指示する。これでAIの事実性やプロンプト攻撃への完全耐性を保証するものではない。未検討論点の公開には引き続き教師の承認を必要とする。

## 録音の形式と再送

Content-Typeの許可リストとコンテナの先頭、音声トラック、読み取れる実際の長さを確認する。申告時間との許容差は3秒または実時間の5%の大きい方。WebMでDurationがない場合は、上限付きEBML走査でBlockの時刻から終端を推定する（最大1秒程度の誤差）。長さが確認できないファイル・破損は拒否し、AIの試行回数を使わない。これは全パケットのデコードによる完全性検証ではない。

送信者・形式・時間・音声内容のSHA-256を録音の指紋にする。完了済みの同一送信は保存済みの受領結果を返し、AIを再実行しない。別の利用者・別の録音を同じグループで追加解析しない。分析中は409で待機させる。プロセス停止時に音声は失われるため、端末が同じBlobを保持して再送する。サーバーに音声そのものを保存せず、解析結果と指紋・受領結果だけを残す。

## 観測とテスト

HTTPログはランダムなrequestId・定義済みルート・結果コード・所要時間、AI処理はランダムなjobId・処理種別・開始/成功/失敗・所要時間のみ。本文、トークン、音声、部屋ID、利用者IDは含めない。ログを受け取る関数の障害で本処理を失敗させない。

`T167_TEST_PORT_OFFSET=10000 bash scripts/dev.sh check` で検査用ポートをずらす。DBプロジェクトは demo-t167-test-10000 として通常プレビューから独立する。使用中のポートは起動前に拒否し、既存サーバーを使い回さない。エミュレータ・モックだけで検査し、クラウドのメタデータ自動検出を無効にする。

check はlint・型・ビルド・単体・Rules・API結合・E2Eに加え、APIのカバレッジと30人/6グループ/3回の同時提出を測る。カバレッジの最低値は行/文85%、分岐80%、関数90%。別Worker内部のカバレッジは親プロセスから集計できないため除外し、実PCMデータとブラウザ録音のテストで検証する。純粋な進行規則を5通り壊す変異検査は、一時ディレクトリだけで行う。これは全バックエンドの変異スコアではない。

負荷試験は外部AI処理を含めず、p50/p95・成功率・提出の欠落・グループ状態を検査する。p95目標は1秒。エミュレータでの値は本番Firestoreの速度・費用の証明にはならない。性能目標を満たさなければ検査を失敗させ、数値を報告する。測定値は api/coverage/local-load.json に残す。

本番のIAM/Rules配備、実Googleログイン、Vertexの実応答、Cloud Runの並行処理・障害復旧、iPad SafariのMP4/WebM・30分録音・画面ロックは別途実機/クラウド検証が必要。DDoS・大量のGoogleアカウントによる分散攻撃の対策はクラウド側の入口制限・App Check等と併せて検証する。今回のローカル実装では本番を変更しない。

## 依存関係

Node 22.12以上を使用し、Zod 4、Firebase Admin 14、Vitest 5を固定する。音声メタデータ検証は music-metadata の修正版を利用する。Next.js 15・React 19・Firebase Web 11の構成は維持し、postcss/grpc等の脆弱な間接依存だけをpackage.jsonのoverridesで更新する。lockfileを使い、更新後のビルド・エミュレータ・ブラウザ検査を必ず実行する。脆弱性監査の0件は監査実行時点の既知アドバイザリに対する結果で、無欠陥の保証ではない。
